# Customer billing centre

The website header's **Billing** link opens `/account/billing` for signed-in customers. The centre combines booking orders and class payments, shows their original currency and status, and provides invoice PDFs for verified booking payments, receipts for class payments, refund history and booking credit-note PDFs. The existing class-payment and booking-detail pages remain available for purchase-specific actions and existing refund requests. Refunds still follow the existing verified provider/admin processing; this page does not issue automatic refunds or create charges.

Saved billing name, address, ISO country code and optional VAT number prefill future booking forms. The customer can review or change them before reserving. A late defaults response never replaces input already edited in the booking form. Email always comes from the account; change and verify it in account settings. Saving or clearing defaults uses optimistic version checks and never changes issued invoices or credit notes. Addresses and VAT numbers are hidden from ordinary profile responses and excluded from billing audit metadata. No saved card details, new recurring subscriptions or card-management UI are introduced. Card entry remains with the existing payment provider.

## History and documents

The server unions owner-scoped `booking_orders` and `payments`, then filters and paginates history at 25 records per page. Search covers purchase title and teacher. Currency and status filters work across historical records, beyond the visible page. All-time totals are computed separately over the full owned history and do not change with filters or pagination. Amounts include charged tax. Each currency is reported independently with original payments, confirmed refunds and refunds in progress; no converted-currency grand total is invented. Bank disputes are shown separately on purchases.

Refund requests are separately paginated at 25 per page. Pending refunds do not reduce confirmed totals until the existing refund worker verifies them. Booking credit notes are downloadable only for their owning order. Class payments use their existing receipt/refund system; receipts are labelled distinctly from tax invoices.

Every history branch and purchase/refund/document lookup enforces the authenticated purchaser id. Teachers cannot download their student's invoice through customer billing. Invoice lookup also checks the issued document's order id; a credit-note id must belong to that same order. Standalone admin invoices are not associated by mutable email addresses. Email changes preserve account-id purchase ownership and the email/name/address snapshots on issued fiscal documents. PDF and personal billing responses use private/no-store caching. Invalid filters and malformed versions fail validation.

## Release checks

Billing reuses existing booking, invoice and payment indexes and workers. The saved user fields are additive and need no data backfill. Preserve issued fiscal documents, refund records and the version counter when rolling back. Do not reconstruct ownership from the current email or rewrite historical invoice recipients.

Real database integration tests cover profile conflicts/privacy, multiple currencies including JPY, paid/open purchases, both invoice/receipt sources, pending/confirmed partial refunds, credit-note ownership, immutable invoice bytes after defaults changes and clearing, and 129 records across six pages. Browser acceptance covers saved defaults, booking prefill/dirty-input preservation, history filters, PDF downloads, real partial refunds, light/dark responsive layouts and selected accessibility rules. Run `npm run test:admin:integration` and `npm run test:account:browser`; evidence is retained by Product and admin CI. Live merchant reconciliation and production release authorization remain governed by [booking earnings](booking-earnings.md) and the [release checklist](release-checklist.md).
