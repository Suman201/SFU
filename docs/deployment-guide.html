02

Free Tier means credits, not a free year.

For eligible new customers, AWS currently grants $100 at signup and offers activities that can earn up to another $100. The Free plan lasts up to six months, ending earlier if its credit balance is exhausted. Check your own balance, eligibility and expiry in the console. AWS Free Tier ↗

While credits last

  • Run the complete, tested deployment.
  • Eligible charges consume the credit balance.
  • The first booked or paid class does not itself switch the AWS account plan.
  • Review credits weekly, including weeks with no classes.

Before the Free plan ends

  • Upgrade the account to Paid to keep the same resources online.
  • Remaining credits continue subject to their actual terms and expiry.
  • After applicable credits, you pay ongoing usage.
  • A year without revenue still has a hosting cost.
Avoid an interruption.

The Free plan closes when its duration or credits end. AWS retains content for a recovery period, but that is not continued service. Set a reminder to review the account with at least 30 days of runway, then check more often as it shrinks. Do not wait for an active class to be interrupted. Account-plan rules ↗

Current AWS documentation lists Lightsail under supported services for the new Free Tier experience. Its newer billing FAQ replaces earlier short trial offers with Free Tier credits. Confirm what your account offers; if a screen asks you to upgrade or activate paid features, read it before proceeding. Avoid relying on older “12 months free” or “90-day Lightsail trial” tutorials. 03

Can GoDaddy shared hosting do this?

Our assessment: it is unsuitable for hosting this complete application on its own. Current GoDaddy plans advertise Node.js, and its Node.js product supports persistent processes and WebSockets. However, its shared-hosting terms exclude inbound UDP; our existing SFU needs browser-reachable UDP media ports. Moving media elsewhere would create a split deployment.

Recording storage needs its own plan.

At an assumed 1.9 Mbps combined recording rate, 100 recorded hours create approximately 85.5 GB each month. That can exceed an 80 GB server disk once the operating system, databases and uploads are included. Use private object storage and a defined retention policy; three months of that recording volume is approximately 256.5 GB before other files. Storage and replay costs must be included in the extras budget. S3 cost components ↗

05

Set up your AWS account and server.

Follow the owner steps in order. Each step includes a result to check. Menu labels can change; linked official guides are the reference. Creating the server starts using credits or accruing charges.

01Create or check your AWS account YOU
  1. Open AWS Free Tier. Use an email address controlled by your business.
  2. If you already have an account, sign in and check its eligibility rather than creating another account to obtain credits.
  3. Choose or confirm the Free account plan if offered. Finish the required identity checks.
  4. Enable multi-factor authentication (MFA). Do not share the main account password or secret keys with a developer.
  5. Open Billing or AWS Settings and note the current plan, remaining credits, credit expiry and Free plan end date.
Check: you can see your own account plan and balance. Do not assume you received the full $200.
02Add cost alerts before creating resources YOU
  1. In the AWS search bar, look for Budgets, then create a monthly cost budget.
  2. For a $24 server, use a starting review threshold such as $35/month. Add your email and actual/forecast alerts.
  3. Track usage cost before credits as well as the remaining credit balance. Credit offsets can make net spend look low while the balance falls.
  4. Set a calendar reminder to review credits weekly and to upgrade before the Free plan ends. Use your actual dates, not dates from this guide.

A budget alert is a notification, not an automatic stop or a spending guarantee. If the current console shows a separate spend-limit feature, read its behavior before enabling it for a live classroom.

Check: the budget exists, the email is correct and you know where to view credits.
03Create one European Linux server YOU + DEVELOPER
  1. Search AWS for Lightsail, then choose Create instance.
  2. Select Europe (Frankfurt) or another agreed European location near your teachers and students. Keep storage and backups in the intended region.
  3. Select Linux/Unix → OS Only → Ubuntu 24.04 LTS, or the current Ubuntu LTS image approved by the developer.
  4. Select a plan with public IPv4. The starting test candidate is 4 GB RAM / 2 vCPU / $24 monthly cap. The 8 GB / $44 plan is the fallback if measurements require it.
  5. Name it sapiovian-main. Recheck the monthly cap, credit treatment and region, then create it.

Linux hosts the backend for all devices. Teachers and students can still use the Windows or Mac app. Do not choose a WordPress blueprint or an IPv6-only plan for this runbook.

Check: one instance is Running in the intended region, with the selected plan.

Official instance creation guide ↗

04Give the server a stable address YOU
  1. Open the instance’s Networking tab.
  2. Choose the option to create a static IP and attach it to this instance. A static IP stays associated with your deployment when the normal dynamic address would change.
  3. Write down the public static address in your private deployment notes.
  4. At your domain provider, add A records for the website, admin portal and TURN hostname, pointing to that address. Keep existing email MX/TXT records.
  5. You can keep the domain at GoDaddy. Changing these DNS records is separate from buying GoDaddy hosting.
Check: all agreed hostnames resolve to the attached static IPv4 address.
05Open only the required network ports DEVELOPER + YOU

In Networking → IPv4 Firewall → Add rule, use the port table below. Match the host firewall and actual deployment settings. A working website alone does not prove classroom media is reachable.

SSH should be restricted to administrator addresses; keep the Lightsail browser-SSH allowance if needed. Leave MongoDB, Redis and the backend’s raw port private. Do not choose “All ports”. Configure IPv6 consistently if it is published in DNS.

Check: the developer has verified the firewall, media addresses and TURN allocation from outside the server.
06Connect to the server safely YOU + DEVELOPER
  1. Open the instance’s Connect tab, then Connect using SSH. This opens the server’s terminal.
  2. Ask the developer to prepare Docker, the reverse proxy and the protected deployment directory. Use a separate administrator identity instead of sharing the AWS account owner login.
  3. The following commands only show server information; they do not install or delete anything.
IN THE SERVER’S SSH TERMINAL · READ-ONLY
uname -m
free -h
df -h /

uname shows the processor architecture, free shows memory and df shows available disk space. The deployment image architecture must match the server.

06

Install the complete product.

This is the developer handoff. You do not need to invent Docker files, database passwords or HTTPS routing. A developer must prepare and verify a versioned deployment package for your host before you run the start commands.

The current repo is a starting point, not a one-click cloud installer.

infra/docker-compose.prod.yml includes backend, MongoDB, Redis, Coturn and monitoring services. It does not serve both website and admin builds by itself. The developer must complete the web/admin ingress, durable private uploads and the reviewed production configuration. Do not deploy the local development Compose file or seed dummy users into the live database.

What you provide

  • The domain and intended website/admin/TURN names.
  • Access through a dedicated administrator identity.
  • A verified sender address and email-provider setup.
  • Your recording retention policy and backup contact.
  • The actual monthly budget and AWS credit dates.

What the developer delivers

  • A Linux-compatible, versioned build of website, admin and backend.
  • A reviewed Compose package using prebuilt images.
  • HTTPS, WebSocket routing, Coturn TLS and private database networking.
  • Secret files, persistent storage, recording storage and backup jobs.
  • A health check, migration/setup steps and a tested rollback procedure.

STUN, TURN and classroom connectivity.
STUN helps discover network addresses. TURN carries encrypted media when a participant cannot connect directly to our SFU. Coturn provides these services on the same server initially, subject to load testing. There is no separate managed-TURN subscription in this plan.

A hostname alone cannot make two independent services listen on the same IP and TCP port. The developer must configure HTTPS/TURN routing before claiming port-443 relay support. Testing only port 5349 does not cover networks that permit only 443. Test real relay allocations, not only a TCP connection or a running container.
Do not disable TURN to save money. Keep credentials short-lived and limit misuse. Include actual relay paths in traffic estimates; hosting TURN beside the SFU does not by itself prove how AWS will meter every packet. Coturn reference · Lightsail firewall guide

Prove the full experience before inviting users.
Use separate teacher and student accounts, two real networks and the actual deployed backend. Local or mocked tests alone do not establish that the public deployment works. Test with the proposed class size and recordings enabled.

09
Keep the same deployment running affordably.
Every week
  • Check remaining credits, underlying usage and the account-plan end date.
  • Review disk space, recording growth and backup success.
  • Confirm login, a classroom join and email delivery.
  • Investigate unexpected traffic or repeated TURN authentication failures.
Before a release or account change
  • Make and verify a fresh backup.
  • Schedule maintenance outside booked classes.
  • Drain the node and follow the developer’s rollback/runbook.
  • Upgrade Free → Paid before expiry; keep the server, DNS and data.


Stopping a Lightsail server does not stop its instance charge.
Ordinary Lightsail instances accrue charges until deleted, including while stopped. Do not delete a full deployment to save a few idle days: profiles, enrollment, reminders, classroom access and recordings depend on the backend. Any future shutdown must first preserve data, backups, keys and a clear recovery plan. Billing behavior ↗


Make savings inside the product
  • Use Teaching/Discussion modes and deliver the video feeds each participant actually needs.
  • Preserve audio and readable teaching content while adapting camera quality.
  • Keep one combined classroom recording and avoid unnecessary copies/conversions.
  • Apply a clear recording-retention policy with expiry information and authorized downloads.
  • Keep the existing backend and shared web/desktop components. Add infrastructure when measurements justify it.
These are development directions; this guide does not certify that each optimization is already implemented. See cost-aware-development.md.

10
The words you’ll see in AWS.
Instance
Your rented Linux computer in the cloud.
Region
The geographical area where that computer and its data live.
Static IP
The stable internet address assigned to your server.
DNS
The records connecting your domain names to the server address.
SSH
A protected terminal connection for administering the server.
Docker / Compose
Tools that run the application’s services together in containers.
HTTPS / TLS certificate
The encryption and identity used by websites and secure TURN connections.
WebSocket
A connection used for live classroom messages and signaling.
SFU
The classroom media server forwarding audio/video between participants.
STUN / TURN
Connection discovery and relay services for participants behind different networks.
Object storage
Private storage for files such as recordings, separate from the server disk.
Snapshot / backup
A snapshot captures a server/disk. A complete recovery also needs databases, files and the private keys that protect them.
