# Customer billing centre

The website header's **Billing** link opens `/account/billing` for signed-in customers. The centre combines booking orders, class payments and promotion purchases, shows their original currency and status, and provides invoice PDFs for verified booking payments, receipts for class payments, refund history and booking credit-note PDFs. Promotion invoices and credit notes open through fresh, validated Stripe-hosted links directly from this centre. The existing class-payment and booking-detail pages remain available for purchase-specific actions and existing refund requests. Refunds still follow the existing verified provider/admin processing; this page does not issue automatic refunds or create charges.

Saved billing name, address, ISO country code and optional VAT number prefill future booking forms. The customer can review or change them before reserving. A late defaults response never replaces input already edited in the booking form. Email always comes from the account; change and verify it in account settings. Saving or clearing defaults uses optimistic version checks and never changes issued invoices or credit notes. Addresses and VAT numbers are hidden from ordinary profile responses and excluded from billing audit metadata. No saved card details, new recurring subscriptions or card-management UI are introduced. Card entry remains with the existing payment provider.

## History and documents

The server unions owner-scoped `booking_orders`, `payments` and `promotion_orders`, then filters and paginates history at 25 records per page. Search covers purchase title, teacher and the immutable promotion plan name. Purchase type, currency and status filters work across historical records, beyond the visible page. All-time totals are computed separately over the full owned history and do not change with filters or pagination. Paid amounts include charged tax. Unpaid promotion rows show the saved plan quote before checkout tax and never count as paid. Each currency is reported independently with original payments, confirmed refunds and refunds in progress; no converted-currency grand total is invented. Bank disputes are shown separately on purchases.

Refund requests are separately paginated at 25 per page. Pending refunds do not reduce confirmed totals until the existing refund worker verifies them. Booking credit notes are downloadable only for their owning order. Class payments use their existing receipt/refund system; receipts are labelled distinctly from tax invoices.

Every history branch and purchase/refund/document lookup enforces the authenticated purchaser id: `studentId` for bookings/classes and `teacherId` for promotions. Historical ownership does not depend on the current email, tutor approval, promotion plan settings or whether new promotion purchases are enabled. Teachers cannot download their student's invoice through customer billing. Invoice lookup also checks the issued document's order id; a credit-note id must belong to that same order. Promotion document links additionally verify the Stripe invoice metadata against the order id; credit notes must belong to a confirmed refund on that order and to that exact invoice at Stripe. Hosted links are fetched on demand, require authentication and use private/no-store caching; payment intent/session ids, customer emails and Checkout URLs are not included in purchase history. The frontend accepts only approved HTTPS Stripe document hosts. Standalone admin invoices are not associated by mutable email addresses. Email changes preserve account-id purchase ownership and the email/name/address snapshots on issued fiscal documents. PDF and personal billing responses use private/no-store caching. Invalid filters and malformed versions fail validation.

Promotion refund requests remain in the existing authorized finance workflow. Customer billing displays queued, pending, confirmed and review states without creating charges or refunds. Only confirmed refunds expose credit notes. Existing promotion purchase/management and finance workspaces remain available. Full promotion refunds remain the supported automated operation; partial or ambiguous external refunds retain their existing review process.

## Release checks

Billing reuses existing booking, invoice, payment and promotion indexes and workers; no billing data migration or financial backfill is required. Deploy the updated frontend and backend together so the new `promotion` source and hosted-document actions are understood by both. Keep the Stripe credentials and promotion reconciliation/document configuration available for historical purchases when disabling new sales. The saved user fields are additive and need no data backfill. Preserve issued fiscal documents, refund records and the version counter when rolling back. Do not reconstruct ownership from the current email or rewrite historical invoice recipients.

Real database integration tests cover profile conflicts/privacy, multiple currencies including JPY, paid/open purchases, both invoice/receipt sources, pending/confirmed partial refunds, credit-note ownership, immutable invoice bytes after defaults changes and clearing, and 129 records across six pages. Browser acceptance covers saved defaults, booking prefill/dirty-input preservation, history filters, PDF downloads, real partial refunds, light/dark responsive layouts and selected accessibility rules. Unified promotion tests additionally cover original JPY and tax-inclusive EUR amounts, unpaid quotes, mixed-source pagination, pending/confirmed refunds, cross-account and cross-order document access, mismatched Stripe invoice metadata, and unsafe hosted links. Run `npm run test:admin:integration` and `npm run test:account:browser`; evidence is retained by Product and admin CI. Live merchant reconciliation and production release authorization remain governed by [booking earnings](booking-earnings.md) and the [release checklist](release-checklist.md).
